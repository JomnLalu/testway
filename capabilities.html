What I can take on

Four kinds of work, each written as a method: what I settle first, what decides the result, and where that kind of project usually goes wrong.

01

Language model fine-tuning

Adapting open models to low-resource languages and narrow domains: assembling the dataset, running the training, then checking the output holds up against real speakers.

The model is rarely the difficult part. The difficult parts are a dataset that teaches the right behaviour and a training setup that fits the hardware actually available. The method follows that order.

  1. Fix the task before the data

    A classifier and a translator need different data, different evaluation and a different interface. I write the exact input and output down first, because changing the task later means changing the dataset. MangARTI changed task once, from classifier to translator, and needed an entirely different kind of data afterwards.

  2. Produce data where none exists

    For a near-zero resource language there is nothing to download. A strong general model drafts source sentences at volume and native speakers write the target side. Every example is stored as an instruction, an input and an output in Alpaca-format JSONL, one example per line.

  3. Fit the method to the GPU

    On consumer hardware, VRAM decides the method. QLoRA freezes the base model in 4-bit precision and trains only small low-rank adapters, which is what lets an 8B model train on a laptop GPU; gradient checkpointing and an 8-bit optimiser cut memory use further.

  4. Judge the output against speakers, not the loss curve

    A falling loss shows that a model fits its data, not that a speaker would accept its translations. Output is checked against how people actually write and talk; a model that scores well and sounds wrong has failed.

  5. Repair the data before the hyperparameters

    On a small dataset, hallucinations usually trace back to inconsistent or incorrect examples. Revising data by hand is slower than launching another training run, and it is the change that actually moves quality.

Then I document where the model stops working: MangARTI's model card says plainly that it translates single sentences and degrades on paragraphs.

02

Python systems

The architecture that turns a model or a data source into a product: request flow, scheduling, storage, and the unglamorous parts that have to keep working after launch.

Start from the contract

Before any code, I settle what goes in, what comes out and what happens when the input is wrong. MangARTI's demo application shows the pattern at small scale. It loads the 4-bit model and its adapter once, builds the Alpaca prompt from the chosen translation direction, rejects empty input before it reaches the GPU, and exposes only the controls a tester needs: output length, sampling, temperature and top-p.

Request flow

Validate early, do expensive work once, and keep each step small enough to test on its own. A request that is going to fail should fail at the cheapest point in the pipeline, not after a model has already spent GPU time on it.

Working with time

Not every system here is Python, but the same rules apply. BSQShuttle, a single JavaScript page, compares the device clock with each route's departures every minute to mark the last bus and the next one. The logic stays simple because the data is shaped around the one question its users ask: when does the next bus leave?

Storage in the shape it is read

Training data lives in JSONL because each line is one complete example that can be read, corrected and reviewed by hand, which is exactly how MangARTI's dataset was repaired. A timetable lives as a list of departures per route, because that is how it is displayed.

After launch

A tool people depend on has to say when it might be wrong. MangARTI's model card lists what it should not be used for. BSQShuttle shows the operator's caveats beside the schedule, including that a full bus may leave before its scheduled time.

When Python is not needed

Python is the default when a model or a data pipeline is involved. When neither is, BSQShuttle and IterMath show the alternative: static pages with no backend, and no application server to maintain.

03

Data science

Getting messy, real-world data into a shape a model can learn from and a person can read: collection, cleaning, and the analysis that decides what to build next.

Collect what does not exist yet

MangARTI's data had to be produced, not cleaned: source sentences drafted, translated by native speakers, then revised by hand. Collection became a project of its own, with volunteers to coordinate and quality to check.

Treat variation as information

Manado Malay (Manadonese) has no standardised spelling, and the same word appears as Ngana, Ngna or ngn. Whether to normalise those forms or teach a model to accept all of them changes how it reads real messages, which makes it a modelling decision rather than a cleaning chore.

Let the analysis decide the product

MangARTI's first model was a Naive Bayes classifier. The most consequential analysis on that project was not a metric: it was a peer's question about who would use a classifier, and the answer turned the work into a translator.

Know the distribution you ship

Measuring the finished dataset explains a model's limits before its users find them. MangARTI's published training file holds 3,454 sentence pairs, each written in both directions, with source sentences averaging under nine words. That is why the model is documented as a sentence-level translator.

04

Hardware electronics

Work that crosses the software–hardware line, where constraints are physical and the margin for a bad assumption is much smaller.

The discipline is the one the software work uses, applied with less room for error: read the specification before relying on it, measure instead of assuming, and change one variable at a time.

The same habit runs through the machine learning work: MangARTI's training was planned around the memory of one laptop GPU, and MangARTI mini is being sized for the devices its users already own.

If a project needs one of these, or the space between two of them, a short description of the problem and the data behind it is the best place to start.

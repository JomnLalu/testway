Where it started

In high school I co-founded Rex Mundi Coding Club, a student-led organisation set up to help other students build practical programming skills. A club like that is measured by what its members can do afterwards, and that is the standard every project here is held to.

MangARTI began as my final school project, and its first version was a classifier. I trained a Naive Bayes model to label text as either Manadonese or formal Bahasa Indonesia. Then a peer asked what anyone would actually do with that label. Speakers already know which language they are reading; what they lack is a way across. The project became a translator built on a fine-tuned large language model, and the question that changed it became the first one I ask of any project: who uses the result, and what do they do with it?

That is also why I work on both halves. Adapting a model to a dialect with almost no training data is half of the job. The other half is building the interface that lets someone use it without knowing what a checkpoint is.

How I choose problems

The problems tend to start close to home: classmates missing the shuttle, students drilling the same math concept without making progress, a dialect that mainstream models have barely seen. Each one is narrow enough to finish and real enough to be used.

Narrow is deliberate. A shuttle timetable for one student residence, a practice tool with seven focused modules, a translator for one language pair: each has users I can name and a definition of done I can check. A tightly scoped project can be finished properly, documented honestly and kept running, and a finished tool is worth more to the people who rely on it than an ambitious one that stays a demo.

Structured systems, not clever models

A fine-tuned model is one component. Around it sits everything that decides whether it is any good: where the training data comes from, who checks it, how it is formatted, what the model is asked to do, and what a person sees when it gets something wrong. I treat that structure as the product.

The dataset is the specification

When early versions of MangARTI hallucinated, the fix was not another round of hyperparameter tuning. It was a rigorous, manual revision of the training data. A model trained on about 7,000 examples reflects every one of them, so reading and correcting the data is the most direct way to change what it does.

Judgement stays with people

Generating text is cheap; deciding whether a Manadonese sentence sounds like something a speaker would actually say is not. In MangARTI's pipeline a general model drafts the source sentences and native speakers write the translations. Automation supplies volume; people supply meaning.

Constraints are design inputs

MangARTI was trained on one consumer laptop with an RTX 5050, and that limit settled the method: a 4-bit quantised base model with small low-rank adapters trained on top. Hardware electronics teaches the same habit, with physical limits in place of a memory budget.

The smallest system that works

Not every problem needs a model, or even a server. BSQShuttle is a timetable stored as data in a single page, with the browser's clock doing the rest. IterMath generates every exercise in the browser and shows the solution after each wrong answer. Choosing that kind of system when it is enough is the same discipline as training a model when it is not.

What I am building now

MangARTI mini: the same translator, rebuilt on models of around one billion parameters so it can run on ordinary hardware. I am experimenting with Qwen and Llama models at that size.
